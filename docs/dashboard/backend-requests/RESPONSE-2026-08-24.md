# BR-010 — `FileDetail`

**All three answers are yes.** Verified against `jovi-mall/src/core/storage/storage-trees.ts`
and `modules/catalog/read-models/file-detail.resolver.ts`, not against a doc.

### 1 · Is `url: string | null` correct?

**Yes.** `toFileDetail` is the single place any `FileDetail` on the platform is built:

```ts
url: isPrivate ? null : storage.getPublicUrl(file.key),
access: isPrivate ? 'authorized' : 'public',
```

`isPrivate` is `isPrivateStorageKey(key)`, which **fails closed** — an unclassified tree is
private. So a tree added next year is `url: null` until somebody classifies it.

### 2 · Is `access` always present?

**Yes, on every route, unconditionally.** `toFileDetail` is the only builder and it always sets
both fields. There is no path that emits a partial `FileDetail`.

One caveat, and it is *not* an exception — it is a different payload that you will never
receive: `VectorisationService` builds its own file shape for an external service, with `url` and
no `access`. It is not a `FileDetail`, it does not reach wi-admin, and it does not reach you.

### 3 · Is `'public' | 'authorized'` closed?

**Yes, closed at two.** It is derived from `TreeVisibility = 'public' | 'private'`, which is a
two-value union in one file. A third value would require a deliberate code change in jovi-mall
plus a matching change in wi-admin's pin — it cannot appear by configuration or by data.

**Keep your open union anyway.** Treating anything unrecognised as *not* displayable is the safe
direction and costs you nothing, and we would rather you were defensive across a service boundary
than trusting.

### What changed on our side

- **`file.gateway.ts`** — `url: string | null`, `access` added, both with the reasoning inline.
  Zero risk: nothing in wi-admin dereferences `url`; the pin is pure pass-through.
- **`files.md`** — worked example for *both* cases, an `access` row, `shipments/` and `digital/`
  named as the private trees, and your `isDisplayableImage` both-conditions rule written out.

### Your acceptance list

- [x] `FileDetail.url` is `string | null` in `file.gateway.ts`
- [x] `FileDetail.access` exists in `file.gateway.ts`
- [x] `files.md` documents `access`, its two values, and what each means for rendering
- [x] `files.md` names `shipments/` and `digital/` as private trees, with `url: null` as expected

      described.** See § *Two things you did not ask about*.

## ⚠ It streams bytes — it does not return a signed URL

**This is the change that affects your code.** You asked for `{ url, expiresAt }` and an
`<img src>`. You are getting the file itself.

**Why.** We checked which storage provider is actually configured before designing anything. It
is **`local`** (`.env`, `.env.example`, and the code default all agree). And `local` **has no
`getSignedUrl` at all** — your capability table has this inverted, see the correction below. So
"return a signed URL" would have meant:

1. inventing a token-signing scheme for local disk, and
2. standing up a **new unauthenticated public route** that serves private bytes to anyone holding
   the link for its lifetime.

That second point is a smaller copy of the exact hole ADR-A01 D-2 was written to close — the
`express.static` mount that made every delivery-proof photo permanently fetchable by URL. We were
not willing to reopen it for this.

Streaming needs no new public surface, is authenticated for the read's whole life, and is the
mechanism the platform's two *existing* private-file routes already use.

### What this costs you

**A bare `<img src>` will not work** — the request needs your bearer token and an `<img>` tag
cannot carry one. Fetch and make an object URL:

```ts
const response = await api.get(`/files/${fileId}/content`, { responseType: 'blob' });
const objectUrl = URL.createObjectURL(response.data);
// render <img src={objectUrl} />
// URL.revokeObjectURL(objectUrl) on unmount
```

**The upside for you:** there is no `expiresAt` to respect, no clock to watch and nothing to
re-request. The object URL lives exactly as long as you keep it. Your "will not cache past
`expiresAt`" logic is unnecessary — drop it.

## ⚠ The permission is named `files.content.read`, not `files.view_private`

You asked for `files.view_private`. We renamed it because we also took your suggestion that the
route answer for **any** file — and once it serves public trees too, "view_private" is a lie in
the permission catalogue.

**Gate on `files.content.read`.**

## The audit

Catalogued as **`files.content.read`**; it appears in `GET /audit/actions` automatically.

- **Fail-closed.** The row commits **before** jovi-mall is asked, and its failure is **not
  caught** — with the audit store unreachable, nothing is disclosed. Same posture as
  `money.payouts.destination.read`.
- **No content and no storage key in the row.** It records *that* a file was opened, which file,
  and what it turned out to be (`mimeType`, `size`). Putting bytes near the audit store would
  make the trail the leak.
- **Recorded in wi-admin, deliberately not in jovi-mall.** jovi-mall authenticates a *service*,
  not a person — a row there would attribute a disclosure to a header the token holder sets. Same
  split as the tracking data door.

**No `reason` required.** We agree with your reasoning: an operator opens many images inside one
dispute, and a per-image prompt becomes a box somebody types "dispute" into forever. Keep
`RevealPositionDialog` where it is — if we ever reverse this it is an additive change and we will
tell you.

## Errors

| Status | Code | When |
|---|---|---|
| 404 | `FILE_NOT_FOUND` | No such file, or it was swept |
| 409 | **`FILE_CONTENT_NOT_SUPPORTED`** | The storage provider cannot read bytes. **Not an outage** |
| 502/503 | `SERVICE_DEPENDENCY_UNAVAILABLE` | jovi-mall unreachable |

**`FILE_CONTENT_NOT_SUPPORTED` is your `FILE_VIEW_NOT_SUPPORTED`**, renamed to pair with the
route and the permission. It behaves exactly as you asked: it is **distinguishable from an
outage**, and on a provider that cannot serve it will be true for *every* file, permanently,
until `STORAGE_PROVIDER` changes.

**Render it as "this platform cannot display private files."** Not an error banner, and **not a
retry button** — a retry will never succeed. `details.platformCode` carries jovi-mall's own
`STORAGE_DOWNLOAD_NOT_SUPPORTED` if you want the origin.

## ⚠ A mid-stream failure cannot become an error status

Once the first byte is sent the status line is committed, so a failure after that point closes
the connection rather than answering a 5xx — you see a **truncated body**, not an error.

That is why we forward `Content-Length`. **Compare it against what you received** before treating
a short image as corrupt. Everything that can fail cleanly — the 404, the provider check, the
audit write — happens before any byte moves.

# Two things you did not ask about

## 🔴 `support.md` told you attachment URLs expire. They do not.

You flagged that support attachments resolve publicly and asked for it to be written down. It was
worse than that: **the page actively asserted the opposite**, and in the reassuring direction.

`docs/api/support.md`, on `GET /support/tickets/:ticketId/attachments`:

> The `url` is minted by jovi-mall's storage provider; **do not cache it past its expiry.**

Verified at `ticket-attachment.service.ts:getAttachmentUrl`:

```ts
return this.storageService.getPublicUrl(fileRecord.key);
```

`getPublicUrl` — a **permanent, unauthenticated public URL**. No signature, no expiry, no session
required. The wording invited a reader to treat the link as self-limiting when nothing limits it.

**If any of your code treats an attachment URL as expiring — refetching on a timer, or declining
to persist it because it "goes stale" — that logic is wrong in both directions.** It never
expires, and it is a shareable secret for as long as the file exists.

Corrected in `support.md` with the real semantics, and cross-linked from `files.md`. Also
documented there: an attachment list row is **not** a `FileDetail` — it is the attachment row's
own shape, `url` a plain `string`, no `access` field. Do not type it as one.

## 🟠 A latent defect in ours, surfaced by BR-011

`getDownloadStream` is what serves **the digital-product download and the delivery-proof
download** — both existing, both live. Neither guards the call.

So **switching `STORAGE_PROVIDER` to `firebase` or `cloudinary` breaks both today**, with a 501
that reads as an internal fault. That is pre-existing and BR-011 did not introduce it; the new
route only makes the condition *reportable*.

It is now recorded in the provider source and in jovi-mall's api-doc, and whoever picks a
production provider owes those two routes a fix in the same change. **Nothing for you to do** —
noting it because it is the same fact behind your `FILE_CONTENT_NOT_SUPPORTED` case, and if that
409 ever starts appearing in production, this is why.
