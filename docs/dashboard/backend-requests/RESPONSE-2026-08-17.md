### Three breaking wire changes

You asked to be told rather than to be surprised. Here they are, in the order they will break
your build.

| # | What changed | Where |
|---|---|---|
| 1 | **Five nested blocks moved to camelCase** — `agent.vehicle`, `agent.device`, `agent.trustSignals`, `agency.policies`, `contract.terms.{employment,remittance,feeSplit}` | `agents.md`, `agencies.md`, `contracts.md` |
| 2 | **`deliveryAgencyId` → `deliveryAgency: { id, businessName }`** on the catalogue row | `vendors.md` |
| 3 | **Vendor `policies` gained content** beside its four booleans | `vendors.md` |

**(1) is the one that matters.** Your types are pinned to the `snake_case` shape deliberately,
so they will break loudly — which is what you asked for. One correction while you retype them:
`agent.vehicle` was *documented* as `{ type, plate }` and was *serving*
`{ vehicle_type, plate_number, color, photo_file_id }`, so the contract and the wire disagreed on
the field names as well as the casing. It is now
`{ type, plateNumber, color, photoFileId }` — four fields, and `type` really is the vehicle type
(`bike` · `car` · `van` · `truck`), not the string `"motorcycle"` the old example showed.

**(2) is a rename, not an addition.** The old key is gone. `businessName` is the Magazin's and is
`null` when it has none.

**(3) is additive.** `hasReturnPolicy` and friends stay, and are now *derived* from the content
rather than being the only thing available.

### Three findings that change what you asked for

#### ⚠️ The tracking pipe had never worked, so DATA-EXPOSURE §1 describes something that was not happening

geo-tracker has been POSTing tracking-state notifications to `TRACKING_STATE_NOTIFY_PATH` —
default `/api/tracking/agent-state` — since the tracking lifecycle shipped. **jovi-mall served no
such path.** Its `/api/tracking` mount had exactly one route, `visible-agents`. A receiver *had*
been built, at `POST /api/internal/agents/:agentId/tracking-state`, and the notifier has never
called it. Delivery is best-effort and a non-2xx is logged and dropped, so neither side raised
anything.

**`last_known_tracking_state` was the schema default on every agent in the database** —
`status: "unknown"`, `position: null`. Your Tracking panel has been correctly rendering an empty
field, and §1's "a person's coordinates ship ungated to tier 3" was describing a disclosure that
could not occur, because there were no coordinates.

That is now fixed in both repos, and the notification carries the position it never carried. So
the exposure question §1 raises becomes live for the first time — see BR-003 below for what was
decided.

#### ⚠️ There is no `accuracyMetres` anywhere on the platform

Not on the notification, not in geo-tracker, not on the wire from the agent app. `grep Accuracy`
over geo-tracker's location domain returns nothing, and its WebSocket `location_update` frame
does not carry one. Adding it starts at a release of the agent mobile application and then
crosses two services.

We did not ship a field that would be `null` on every row in every circumstance — that teaches a
client to expect data that does not exist. It is documented as absent, with what it would take.

#### ⚠️ There is no `emailVerified` on a user, so `USER_CHANNEL_UNVERIFIED` does not exist

BR-001 §2 proposed refusing an unverified destination. jovi-mall's `users` row carries no
`email_verified` — verification flags live on the **role** entities (a vendor's, an agent's), a
user may hold several roles, and `login_email` is the login identifier itself: the address
`POST /auth/forgot-password` already mails a live reset token to, anonymously, with no check at
all.

Gating the administrator path more tightly than the path an attacker can drive protects nothing,
so there is no such code and no such gate. Recorded in `errors.md` so nobody adds one later
believing it was an oversight.

# BR-001 · Credential recovery — **built**

Two routes, both delegated, both audited.

```
POST /api/v1/users/:userId/password-reset-link    users.password.reset
POST /api/v1/users/:userId/login-link             users.login_link.send
```

Body `{ channel: 'email' | 'whatsapp' | 'telegram', reason }`, strict. Response is exactly the
thin shape you proposed, plus a `kind`:

```jsonc
{ "kind": "password_reset", "channel": "whatsapp",
  "destinationMasked": "+2376••••4417",
  "expiresAt": "…", "sentAt": "…" }
```

Full contract: [`users.md`](../../api/users.md), the "Credential recovery" section.

### Your seven design questions, answered

**1. Link semantics.** Single-use and expiring, as you suggested — but the numbers come from the
flows that already existed rather than from new policy. Reset: **30 minutes**, redeemed at the
existing `POST /auth/reset-password`, carrying the `password_changed_at` stamp that evicts every
live session. Login: **10 minutes**, and it is a link *and* an 8-character code for one session —
using either kills the other. Re-issuing for the same party revokes the previous credential, so
an operator who clicks twice leaves one live link, not two.

**2. Unverified destinations.** No gate. See the finding above.

**3. Rate limiting.** Per party **and** per administrator, and neither substitutes for the other:
the first is a harassment and SMS-bill bound (the party did not ask for any of this), the second
bounds a compromised operator account. `USER_CREDENTIAL_LINK_THROTTLED` carries
`details.scope: 'party' | 'administrator'` — the two have different remedies, so the distinction
survives to your screen.

**4. Enumeration.** Not applicable in the way you feared, and worth saying why: the caller is
authenticated and permissioned, and out-of-scope records already 404 by the existing rule. What
the endpoint *does* refuse loudly is a suspended account — unlike the self-service path, which
must stay silent because its caller is anonymous. An administrator looking at the account gets
`AUTH_ACCOUNT_SUSPENDED` and knows to reinstate first, rather than wondering whether it sent.

**5. Dual control.** **No** — considered and declined. Four-eyes guards three actions today, all
irreversible or privilege-granting. A reset link is neither. Making routine account recovery a
two-person job pushes operators toward reading passwords over the phone, which is the workflow
this replaces. You need not render "waiting for approval" here.

**6. Which permission.** `users.password.reset` is routed and has left the `†` list, as you
suggested. But the login link got **its own new permission**, `users.login_link.send`, and that
is a deliberate split rather than tidiness: a reset link grants nothing until the person chooses
a password, while a sign-in link *is* a session — whoever opens the message is signed in as that
customer. One permission would have meant granting "help people back in" silently granted "sign
in as a customer", with nothing in the trail to tell the two acts apart.

**Neither reaches tier 3**, as you asked. `test:users` asserts the absence, because
`assertGrantTableValid()` cannot catch it: neither permission carries a `financial` or
`destructive` flag.

**7. Telegram.** **In scope, and it works** — your reading that it would need a new `chatId`
field turned out not to hold. The platform stores no `chatId` on a party, but
`channel_connections` already *is* the `(user, channel, external_id)` mapping, populated when
somebody runs `/connect` with the bot. A party who has connected has a chat to reach; one who has
not gets `USER_CHANNEL_UNAVAILABLE`, which is the honest answer rather than a gap.

### One thing that is narrower than you proposed

**The login link is customers only.** `USER_LOGIN_LINK_ROLE_UNSUPPORTED` for everybody else, and
the refusal is structural rather than configurable: jovi-mall's `MessagingLoginService` scopes
every session it mints to `customer` as a literal, because a vendor, agency or agent reaches money
and other people's data. Send them a **reset link** instead.

This matches the operator's own words — *"a login link to customers, and a reset-password link to
vendors, agencies and agents"* — so we do not think it costs you anything. Worth knowing why it is
not a switch somebody can flip.

### Acceptance

- [x] Both routes exist, are delegated, and are audited
- [x] `channel` is a pinned enum; an unknown value is a `400`
- [x] The destination is read from the party's record and never accepted from the caller
- [x] The response carries no token and no unmasked destination
- [x] Links are single-use and expire; issuing a new one invalidates the previous
- [x] Rate-limited per party and per administrator, with the wait in `details.retryAfterSeconds`
- [x] Decisions recorded on unverified destinations (no gate — the field does not exist), dual control (no), and Telegram (yes, via `/connect`)
- [x] `users.password.reset` routed and out of the `†` list; **not** granted to tier 3
- [x] New codes in `errors.md`; new actions in the audit catalog

> **One deviation worth flagging.** `Retry-After` as a header is not set — the wait arrives in
> `details.retryAfterSeconds`, which your API client already reads (it parses the header *and*
> falls back to that field). The refusal originates in jovi-mall and reaches you as
> `PLATFORM_OPERATION_REJECTED`, so the header would have to be reconstructed at the boundary
> from a code-specific rule. Say the word if you want it and we will add it.

# BR-002 · Totals and owner names on earnings accounts — **built**

`GET /money/earnings/accounts` now returns exactly what you proposed.

```jsonc
"data": [ { "owner": { "type": "vendor", "id": "665a…", "name": "Douala Fresh Market" },
            "pending": …, "available": …, "reserve": …, "requested": …,
            "currency": "XAF", "updatedAt": "…" } ],
"meta": { "total": 431, "page": 1, "limit": 20, "pages": 22,
          "totals": [ { "currency": "XAF", "pending": …, "available": …, "reserve": …, "requested": … } ] }
```

**Your distinction was the right one and we adopted it verbatim.** The sum across the four
balances for one owner stays forbidden — `requested` is a claim already staked against
`available`, so it double-counts. The sum down one balance across owners is a different question
with the same unit and the same direction, and jovi-mall computes it because it is the only party
that can see past page 1.

Note the row shape changed slightly from what you traced: **`ownerType`/`ownerId` are now
`owner: { type, id, name }`**, matching how every other money row on this service names its
party. Your `isEarningsAccountRow` guard will need one line. The endpoint is typed on our side now
and documented, so the guard is a belt you can keep or drop.

`ownerName` is hydrated **in wi-admin**, using the same `hydrateOwnerNames` that `listPayouts`
calls four lines away — you spotted that, and you were right that it was applied inconsistently
rather than deliberately withheld.

### `sort` and `search` — the recorded decision

**Neither is offered, and the "no sorting" line stays.** `search` is refused for a reason worth
having in writing rather than inheriting: the platform pages this by `available_balance`, and a
search term would have to match a name living in a third collection — the join the `ownerName`
above performs *after* paging. Searching before paging means joining before paging, which is
exactly what makes the agency directory the one list on this service that cannot use an index for
its sort. An operator with a specific owner in mind should go through that owner's directory and
follow the link to `/accounts/:ownerType/:ownerId`, which is the complete server-side answer for
one party. Written into `money.md`.

### Acceptance

- [x] `meta.totals` is an array, one entry per currency, over the whole filtered result set
- [x] It respects `?ownerType=`
- [x] It carries no sum across the four balances
- [x] `owner.name` on every row: business name, else contact name, else `null` — never `""`
- [x] `money.md` has a response block for this endpoint
- [x] A decision is recorded on `sort` and `search`

# BR-003 · Naming the last-known position — **built, and the pipe behind it repaired**

Start with the finding at the top of this document: **the field you were asking us to name has
never held a coordinate.** Three repositories changed to make this request answerable at all.

- **geo-tracker** — the tracking-state notification now carries `position: { latitude, longitude,
  recordedAt }`. Named fields rather than a GeoJSON pair, so the `[lng, lat]` inversion happens
  exactly once and on the side that stores it. Omitted when there is no fix, which is common on
  precisely the transitions that get sent.
- **jovi-mall** — serves the advertised `POST /api/tracking/agent-state`, and reverse-geocodes the
  position **once per position**, storing the result.
- **wi-admin** — projects it.

```jsonc
"lastKnown": {
  "status": "streaming",
  "position": { "type": "Point", "coordinates": [9.7043, 4.0511] },
  "place": { "label": "Bonapriso, Douala, Cameroun",
             "source": "reverse_geocode:nominatim",
             "resolvedAt": "2026-08-13T08:41:14.000Z" },
  "reportedAt": "…", "source": "geo_tracker", "isStale": true
}
```

Exactly the shape you proposed. `place: null` when nothing resolved; `source` is an open string
naming the resolver, so render it raw and do not `switch`. Coordinates remain `[lng, lat]`, and
`agents.md` now says so beside the field.

### The exposure question, answered

**Decision: `lastKnown` stays under `agents.read`. No new permission, no audited read.**

Your reading — that a last-known position is a historical record, that withholding it is harmful
in exactly the situation an operator opens the screen for, and that a denied tracking verdict
means *do not track them now* rather than *erase where they were* — was accepted as the product
position. `DATA-EXPOSURE-REGISTER.md` §1 should be closed against it, noting the pipe finding
above: the disclosure it flagged had not been occurring, and now that it can, the decision is that

Your client-side treatment stands and we would keep it: the freshness badge above the reveal, the
coordinates behind an explicit action, no embedded map. The refusal of a static pin is right — and

live-looking lie rather than an empty panel.

### `accuracyMetres` — not deliverable

See the finding at the top. Documented in `agents.md` and in
`geo-tracker/api-doc/tracking-notifications.md`, with what it would take.

### Acceptance

# BR-004 · Contract read and administration — **built, in the shape you recommended**

### The read

```
GET /api/v1/contracts/:contractId     agencies.read + agents.read
```

Its own mount rather than a path under `/agents` or `/agencies`, for the reason you gave: a
contract belongs to both and to neither, and a caller holding only a contract id should not need
an agent id first. Carries `ContractCore` plus **both** decorations. New file:
[`contracts.md`](../../api/contracts.md).

### The writes — three of six

```
POST /api/v1/contracts/:contractId/suspend      agents.contracts.manage
POST /api/v1/contracts/:contractId/reinstate    agents.contracts.manage
POST /api/v1/contracts/:contractId/terminate    agents.contracts.manage
```

**Your argument was accepted.** *"Do not let an administrator impose terms"* and *"do not let an
administrator stop an abusive relationship"* are different claims, and only the first had ever
been made. Each write runs jovi-mall's own agency-scoped transition with the contract's own agency
resolved from the row, so the authority matrix, the legal `from` states and the membership-event
history are the same code an agency desk runs — a different **door**, never different **rules**.

Your position table, with our verdicts:

| Action | Your reading | Ours |
|---|---|---|
| Suspend / reinstate | The strongest case | **Agreed. Built.** |
| Deactivate / terminate | Same argument, terminal | **Agreed. Built — with a caveat below** |
| Approve a pending contract | Recommend refusing | **Agreed. Refused**, recorded in `agents.md` |
| Edit terms / counter-offer | Recommend refusing | **Agreed. Refused** |
| Adjust the COD slice | Genuinely ambiguous | **Refused**, and on a third ground rather than the terms one — see below |

**The COD slice.** Refused, and your instinct about the blast radius was right, but the deciding
reason is different from the terms argument: `cod.threshold` is bounded across every allocating
contract by `agent.cod.maxThreshold`, and the arithmetic that bounds it is one service's. Rather
than build a write whose validity depends on rules we would have to not pre-check,
`PUT /agents/:agentId/cod-threshold` already sets the agent's whole pool with that arithmetic
applied — that is the lever, and it is `financial` and tier-2.

### ⚠️ Terminate routinely does not terminate

The one thing to build your UI around:

```jsonc
{ "success": true,
  "data": { "contract": null,
            "pendingRequest": { "id": "665e…" },
            "blockers": { "outstandingCod": 42000, "outstandingPayment": 18500, "clear": false } },
  "message": "Termination requested — it completes once the counterparty agrees and the outstanding balances are clear" }
```

Deactivation needs the counterparty's agreement **and** the outstanding COD settled and the agent
paid. **Branch on `data.contract`, never on the status.** There is no override and there will not
be one — ending a relationship that still owes an agent money is how that money stops being
anybody's responsibility.

To your dual-control question: not added. `blockers` makes the outstanding-balance case
*impossible* rather than merely reviewable, which is the stronger guarantee.

### Documentation and casing

Both fixed. `terms.employment`, `terms.remittance` and `terms.feeSplit` are documented field by
field in `contracts.md` and mapped to camelCase — **this is breaking change (1)**. The four traps
you wrote your panel around are all now stated in the contract rather than only in your code:
`coverageRegions: []` means all regions, `proposedBy` (not `origin`) decides whose turn it is,
`feeSplit` is the only money block carrying a currency, and `remittance.dayOfWeek` is `0 =
Sunday`.

### Acceptance

- [x] `GET /contracts/:contractId` exists, gated on both read permissions, carrying both decorations
- [x] `terms.employment`, `terms.remittance`, `terms.feeSplit` documented field by field
- [x] Their casing is fixed to camelCase **and announced** (breaking change 1)
- [x] A written position exists on each of the six actions
- [x] Every new write is delegated, reasoned, audited and catalogued

# BR-005 · Product detail — **built**

```
GET /api/v1/vendors/:vendorId/products/:productId     vendors.read
```

Scoped by both ids, so a `404` covers "no such vendor" and "not this vendor's product" alike.
Full contract in [`vendors.md`](../../api/vendors.md).

Every block you asked for is there — `media`, `pricing`, `inventory`, `deliveryAgency`, `storage`,
`variants` — with three differences worth reading.

### `media` — resolved, not ids. **Gap D2 is closed.**

You asked us to treat D2 as part of this request, and we did, but more broadly than the product:
there is now a general resolver.

```
GET /api/v1/files?ids=a,b,c     files.resolve   (1..100)
GET /api/v1/files/:fileId       files.resolve
```

New file: [`files.md`](../../api/files.md). **`files.resolve` is granted to every tier including
Support**, because the caller is already holding an id they were allowed to receive.

That unblocks every `*FileId` on the dashboard, not just product images — avatars, store logos,
banners, agency logos, delivery proofs, the new `vehicle.photoFileId`. Two things to know:

- **The batch response may be shorter than the request and is not in request order.** Files are
  soft-deleted and swept, so a record legitimately outlives its picture. Key by `id`. The single
  form does 404, because a caller who asked for one file cannot otherwise tell "gone" from "the
  field was empty".
- **Check `mimeType` before rendering an `<img>`.** A product's media may hold a video or a spec
  sheet; the first entry is the thumbnail by convention, not by type. (The product detail's
  `media.images` is already filtered to `image/*` for you — this applies to ids you resolve
  yourself.)

The product detail resolves its own images inline, so the common case is still one request.

### `storage` — `monthlyEstimate`, not `accruedThisPeriod`

Your instinct that the multiplication should not happen in a browser was right, and it turned out
the platform does not do it either.

**jovi-mall does not track, invoice or act on storage payment.** The rate has been collected at
agency onboarding since day one and has never been charged — the earnings split deliberately
excludes it, because it is rent rather than a delivery fee. The only platform lever attached to it
is the agency's own manual suspension.

So what you get is the platform's own quote, from the same pure function the agency's inventory
screen uses:

```jsonc
"storage": { "basis": "per_sku_monthly", "storageBasedEnabled": true,
             "monthlyRatePerSku": 500, "quantity": 42, "monthlyEstimate": 21000,
             "currency": "XAF", "size": null }
```

`monthlyEstimate` is what the agency *should be charging* to shelve this listing, which it
collects out of band. A field claiming what the vendor *owes this period* would be an invoice this
platform has never issued — so your "a rate we can attribute is far better than a number we
invent" is exactly the line, and this is one step better than the bare rate.

`storageBasedEnabled: false` is your `billable: false`, and means the agency does not offer
warehousing at all — so the block is never silently zero. `storage: null` when the listing is not
warehoused by an agency at all (digital, or collected from the vendor's own address); **`null` and
zero rent are different facts.**

`size` is on each variant, for sanity-checking the rate — **never a multiplier**, the rate is flat
per SKU. `source` says whether the dimensions came from the variant or the product's shipping
defaults.

### `inventory` — `tracked` is there, and the roll-up has a rule

`inventory.tracked: false` distinguishes untracked from zero, exactly as you asked. Two additions:

- `reserved` is real — units held mid-checkout, using the same filter checkout itself enforces —
  and `sellable` is `available − reserved` floored at zero.
- **At product level, `tracked` is `false` if *any* active variant is infinite-stock.** A product
  one of whose units is uncounted has no honest total, and reporting the countable subset would
  understate availability.

`variants` includes **archived** ones (check `status`): a listing that went wrong is what an
administrator opens this screen to understand, and hiding the archived unit makes a product with
one archived variant look like a product with none.

### `deliveryAgency` on the list too — **breaking change (2)**

`deliveryAgencyId` is gone from the catalogue row, replaced by
`deliveryAgency: { id, businessName }`. That removes your N+1 *and* the permission question:
the name now arrives under `vendors.read`, so your `can('agencies.read')` gate on that tab can go.

Resolved as the product's own override, else the vendor's default — the same precedence the
activation gate uses. `null` for the whole block when neither names one, which is a real
diagnostic state: a physical product in that condition cannot be activated.

### Acceptance

- [x] `GET /vendors/:vendorId/products/:productId` exists under `vendors.read`, scoped by both ids
- [x] Returns `media`, `pricing`, `inventory`, `deliveryAgency`, `storage` and `variants`
- [x] `inventory.tracked` distinguishes untracked from zero
- [x] `storage` carries the agency's rate and whether the listing is billable (`storageBasedEnabled`)
- [x] `deliveryAgency` is an object carrying `businessName`
- [x] **File-URL resolution ships alongside — gap D2 is closed**, and generally rather than for products only
- [x] `vendors.md` documents the response; the `platform_oversight` / vendor-restore interaction is stated on both routes

# BR-007 · Owner-scoped subscriptions — **built, Option B and Option A**

You said either would do and that B was better. Both shipped, because A costs almost nothing once
B exists and it closes the addressability gap you named.

```
GET /api/v1/billing/subscriptions/:ownerType/:ownerId    billing.plans.read
GET /api/v1/billing/subscriptions/:subscriptionId        billing.plans.read
```

No path collision — two segments versus one.

```jsonc
{ "data": { "owner": { "type": "vendor", "id": "665a…", "name": "Douala Fresh Market" },
            "current": { … } , "queued": { … }, "history": [ … ] },
  "meta": { "total": 7 } }
```

Exactly your shape. **`current` is the row whose `status` is `active`** — the platform's own
determination, and a partial unique index upstream guarantees there is at most one. `queued` is
the `pending_activation` row. Unpaginated: an owner accumulates one term per renewal, so paging
would add a cursor to answer a question that fits in one response and would reintroduce the
straddling problem it exists to remove.

`current: null` means **no active plan**, not "we could not determine it" — the same fact
`GET /accounts/:ownerType/:ownerId` reports by nulling its subscription block. A `404` is only for
an owner that does not exist; an owner who has never had a plan gets `current: null` and an empty
`history`.

A row with an **unrecognised** status lands in `history` rather than being dropped, matching your
rank function's behaviour.

You can now drop the client-side grouping, the status-rank heuristic and the "this page only"
caveat. Keep the `BILLING_PENDING_PLAN_EXISTS` pre-emption — but read it off `queued`, which is
complete, rather than off whatever the page happened to contain.

### The two smaller things

**The status vocabulary is written down** in `billing.md` as an open list: `active`,
`pending_activation`, `expired`, `cancelled`, with "known members, open for a fifth" stated
explicitly and the instruction to rank an unrecognised value as history rather than drop it.

**`BILLING_PENDING_PLAN_EXISTS` is documented** on the assign route, with a note that it is
reachable on a completely ordinary path.

# BR-009 · Log detail — **the decision you asked for, and the declaration you wanted**

### 1. `GET /audit/legacy/:id` — **not built**, and that is the recorded decision

You said you would rather have the decision than the endpoint, and leaned toward no. Agreed, with
the reason now in `audit.md`:

A legacy row **already carries everything the writer stored** — unlike an `AuditEntryDto`, whose
detail route adds `payload`, `before`, `after` and `stateTruncated`, four fields the list
deliberately omits. A detail route here would return the row you are already holding. What it
would add is addressability, against a module that is deleted at cutover.

`audit.md` now says the legacy feed is list-only by design, so the absence stops reading as an
omission next to `GET /audit/:auditId`.

### 2. A declared shape for platform log entries — **done**

Documented under `GET /system/platform/logs` in [`system.md`](../../api/system.md), with a
pointer from `dev-tools.md` (the route is mounted under `/system`, not `/dev-tools` — worth
knowing, since your request looked for it in the latter).

```jsonc
{ "at": "…",        // always
  "level": "error",  // always — and the filter is AT OR ABOVE
  "msg": "…",        // always
  "requestId": "…" | null,
  "err": { "type", "message", "stack" },   // when the line carries an error
  "res": { "statusCode": 500 },            // when the line closes a request
  "…": "any further keys the writer attached" }
```

Partial by design, exactly as you proposed: guaranteed keys named, everything else declared as the
writer's context and rendered raw. Same posture the contract takes on unknown enum members.

### 3. The two confirmations

**Nothing is truncated server-side.** There is no `stateTruncated` equivalent and none is needed —
a line is stored as the writer emitted it, so a long `err.stack` arrives whole. (Audit rows *are*
truncated and say so; log lines are not.) Now stated in `system.md`.

**`meta.warning` stays on the response.** Confirmed and written into the contract, with the reason
you gave: you render it from `meta` so the current wording travels rather than a copy that drifts.

### Acceptance

- [x] `audit.md` records that the legacy feed is list-only by design
- [x] `dev-tools.md` declares the guaranteed keys and states that further keys are the writer's context (in `system.md`, where the route lives, with a pointer from `dev-tools.md`)
- [x] Whether any log field is truncated server-side is documented — **nothing is**
- [x] `meta.warning` stays on the response

# What we did not do

Stated plainly rather than left for you to discover.

### DATA-EXPOSURE §6 — three order writes still return the raw platform document

**Not fixed, and it is the largest thing left on your register.** `POST /orders/:orderId/cancel`,
`/dispute/resolve` and the `order` half of `/dispatch` still forward jovi-mall's entire Mongoose
document, including `delivery_address.coordinates` and `raw_input` — the fields the corresponding
*read* deliberately withholds.

It is outside all nine requests, which is the only reason it is not in this change. Your
mitigation (discarding `data` entirely in `orders.service.ts`, structurally rather than by
discipline) is the right one and should stay. We recommend it as the next item, and the fix is the
one you named: map the write responses through `toOrderDetailDto`, which is one call away since
we already re-read the order to build the audit `before`.

### DATA-EXPOSURE §3 — fixed, though you did not ask in a BR

`PUT /agents/:agentId/cod-threshold`'s audit row recorded `after.codMaxThreshold: null` on every
write, because `asState()` read `agent.cod?.maxThreshold` while the endpoint answers a
`CodAllocation` with `maxThreshold` at the top level. Both shapes are read now, the
`Promise<PlatformAgent>` annotation is corrected, and `agents.md` documents the real response
shape — it had said "the updated agent".

### DATA-EXPOSURE §4, §5, §7 — recorded positions, no change

- **§4 (residual personal data on `/agents` at tier 3).** Confirmed intended as-is. `device.*` and
  `homeBase.label` answer genuine dispatch questions, and a narrower Support projection would make
  "why can this agent not be assigned" unanswerable at the tier that asks it most.
- **§5 (agency KYC identifiers).** No change; business identifiers rather than personal ones, and
  appropriate for an administrator. `policies.documents[]` is now documented as off-platform links
  this service never fetches.
- **§7 (the COD block on a shipment under `shipments.read`).** Confirmed intended. A support agent
  answering "the driver says he never got the cash" needs the collection state, and withholding it
  pushes them toward a surface they cannot reach. The delivery code itself stays excluded twice
  over.

### Not in scope, and not close

**A live position for administrators.** Unchanged, and ADR-009 D-2 stands: every geo-tracker data
read needs a real platform user JWT and resolves visibility by looking that user up in `users`,
and a wi-admin administrator has no `users` row, deliberately. Opening it means either minting
platform user rows for administrators or giving geo-tracker a service-caller identity. As you
said — its own request, and a large one.
