# BR-019 § 1 — read this first, because you are shipping on a false premise

You asked us to confirm option (a): *"`translations` is returned in creation order, oldest first,
and that order is stable."*

**It is false, and the way it is false is worse than the deploy risk you were guarding against.**

`mergeTranslations(existing, incoming)` returns `incoming.map(…)`. `existing` is consulted only
for slug history. `PATCH` replaces the whole array and stores it in the order it was sent. So:

> **`translations[0]` is the first element of whichever array was PATCHed most recently — not the
> language the article was created in.**

Your BR worried that a `$sort` we added for tidiness could silently repoint the driver. The real
exposure is nearer: **a client that sorts translations for display and sends them back repoints the
driver itself**, with a request that cannot fail. Measured, not read — a merge of `[fr, en]` over a
stored `[en, fr]` comes back `[fr, en]`.

**Shipped: your option (b).** `sourceLocale` on `AdminArticleDto` and `AdminArticleSummaryDto`,
derived at create from the first translation, **never written by `PATCH`**.

Two properties worth knowing:

- For rows with no stored `source_locale` the DTO answers `translations[0].locale`. That is not a
  backfill dodge — nothing seeds articles (jovi-mall's `seed:blog` writes the byline only), so
  every such row was written by this editor in create order, and the fallback is correct **for the
  existing population specifically**.
- `sourceLocale` is guaranteed to name a locale **present in `translations`**, because a
  full-array replace can drop the source language.

⚠ **A bug fell out of this, in the area you were working in last round.**
`ARTICLE_LIST_PROJECTION` was missing `translations.cover_alt`, so **every row of your article
list reported `coverAlt: null`** — indistinguishable from "nobody wrote one", on the single field
whose purpose is to warn that a publish will be refused. Fixed and pinned.

# BR-015 — the media library, and the first file this service can create

Design record: **`admin/docs/ADR-021-ADMIN-MEDIA-LIBRARY.md`**. It amends two things that were
written as settled, and says so in both places rather than leaving them to rot.

## The three decisions, and the one that went against your recommendation

| | Decision | Note |
|---|---|---|
| **D-1** | The library is a **direct read** of `jovi_mall.files` + `file_references` | Not delegated. It keeps working while jovi-mall is down |
| **D-2** | Upload is a **stream proxy** through wi-admin | ⚠ **Not your option 1 (the ticket).** See below |
| **D-3** | wi-admin **builds public URLs itself** | ⚠ This **reverses ADR-009 D-6**, knowingly |

**Your option 3 was not rejected — it is impossible.** Re-opening jovi-mall's
`POST /api/files/upload` to an `admin` session cannot work: `admin` was removed from jovi-mall's
auth role enums at Phase 5 Part B, so **an administrator holds no jovi-mall session to present**.
Your instinct not to choose it was right for a stronger reason than you gave.

**Your option 1 (the upload ticket) was declined**, and the reason is the line your own BR
quotes elsewhere: the browser posting bytes straight to jovi-mall breaks *"an admin never calls
jovi-mall"* (`README.md`, first line), needs your origin added to jovi-mall's `ALLOWED_ORIGINS`,
and stands up a token-authenticated upload route on jovi-mall's public surface.

What we took instead is your option 2, **narrowed until the objection to it disappears**:
wi-admin pipes the raw multipart body through **without ever parsing it**. No new dependency
(no multer, no busboy), no bucket, no signing key. The rule *"wi-admin accepts no multipart
bodies anywhere"* is **narrowed to "wi-admin never parses one"** — amended in writing, not
quietly broken. Your 1 MB body limit was never the obstacle you thought: `express.json` is
content-type gated, so a multipart request was already arriving unparsed.

## Your four explicit questions, answered

**1 · `limit` — 100 wins.** jovi-mall's 50 does not apply; this read never reaches that validator.

⚠ **But `sortBy` + `sortOrder` do NOT work here.** This service takes a single `sort` token
(`sort=-createdAt`). Getting it wrong is **silent** — the list-query schema is not `.strict()`, so
`sortBy=size` returns a `200` in the default order with nothing saying your sort was dropped.

**2 · Audited — no**, and we know that is the opposite of your recommendation.

Your argument was the strongest available: this route *enumerates*, and the reasoning that makes
`files.resolve` safe for every tier does not survive a listing. We still went the other way, for
one reason: **`files.orphans.read` already enumerates on this same mount and is not audited.**
ADR-006 D-5's exception test is *"the output IS the disclosure"* — which is what makes
`files.content.read` (the bytes) an exception, and which a metadata listing fails.

**Adding it later is additive** — a `audit: records(...)` line and a catalogue entry. If you think
the enumeration argument should beat the precedent, say so and we will take it; this is a
judgement call and yours is a reasonable reading of it.

**3 · Which tree does an admin upload land in — PUBLIC.** `POST /api/files/upload` writes
`by-type` folders (`images/`, `documents/`, …), all classified `public` in `storage-trees.ts`. So
an admin-uploaded blog image gets a real `url` and `access: "public"`. **The blog half of your
request closes.** No configuration, no caller flag.

**4 · Constraints, declared not discovered:**

| | Value | Enforced by |
|---|---|---|
| Max bytes | **32 MiB**, whole request body (`ADMIN_UPLOAD_MAX_BYTES`) | **wi-admin**, before the hop |
| Max files | 10 | jovi-mall |
| Field name | **`files`** | jovi-mall |
| Accepted MIME | `image/jpeg` `image/png` `image/webp` `image/gif` `application/pdf` `application/zip` `audio/mpeg` `audio/wav` | jovi-mall |

⚠ **Only the byte ceiling is enforced here.** This service never parses the body, so it cannot see
a part boundary or a per-part content type. The other three are **published, not policed** — filter
your file dialog with them. A file that slips past comes back as `PLATFORM_OPERATION_REJECTED`
with `details.platformCode: "UPLOAD_POLICY_VIOLATION"` and a `details.violations[]` array. That is
a normal refusal, not a bug.

32 MiB is wi-admin's number, not jovi-mall's 2 GB. jovi-mall's own policy caps an image at 10 MB
and a PDF at 25 MB, so this is the largest artefact it will accept plus multipart framing.

## Two things on the row shape you should design around

⚠ **`usage` is NOT the exact complement of `referenceCount`.** `usage=unused` means jovi-mall has
stamped `orphanedAt`; `used` means it has not — **which includes a file never attached to
anything**. A file uploaded a minute ago reports `usage: used` **and** `referenceCount: 0` on the
same row. That is not a contradiction: the filter is the indexed answer, the count is the precise
one. **Render the count.**

⚠ **The `provider` filter accepts six values, three can exist, and two produce a URL.** Six is
`IFile.provider`'s Mongoose enum. Only `local`, `firebase` and `cloudinary` are implemented —
`s3`/`gcs`/`r2` have **no provider implementation in jovi-mall at all**. And wi-admin can
reproduce the URL form of only **two** of those three: under `cloudinary`, every `url` is `null`
and **`meta.publicUrlsConfigured` is `false`**. Branch on that flag rather than inferring from a
page of nulls.

`meta.referenceSampleCap` is `5` — you asked for the cap to be on the wire, and it is.

## ⚠ § 6 — you pointed us at the wrong field

You wrote that `order.vendorName` should be *"the vendor's `businessName`"* and named

You asked for "the closed list, or a statement that it is genuinely open". `EntityType` is a

You also get `entity.vendorId` (for `PRODUCT`) and `entity.label` (order number, tracking number,

# BR-018 — vendor's agency connections

**`GET /api/v1/vendors/:vendorId/agencies`**, guarded `vendors.read` **+** `agencies.read` — the
composite you asked for, for the reason you gave.

## Your transport proposal was wrong, and the correction is in your favour

You proposed `Transport: Delegated`. It is a **direct read**. `vendor_agency_connections` has been
declared readable since Phase 6, and **two shipped endpoints already read it directly** — the
`counts.agencyConnections` block you quoted, and `policyVersionPausedConnections` on the agency
detail. A third reader of the same collection cannot be the one that needs a gateway.

## `productCount` is cheap — you get the column

You asked, and said you would rather lose the field than have a slow endpoint. **You lose nothing.**

The expensive shape was the one you assumed, not the one that exists: `countDocuments` per row
would be nine scans of one catalogue producing nine numbers that can disagree if a product moves
mid-flight. What shipped is **one `$group` over the vendor's catalogue for the whole page**, served
by the `vendorId` prefix of an existing index — the same index, range and plan
`GET /vendors/:vendorId` has already been paying on every call since Phase 6. **One query per
request regardless of page size.**

We also built your alternative: **`GET /vendors/:vendorId/products?deliveryAgencyId=…`**. Its
`meta.total` equals `productCount` **by construction** — both go through one shared
`resolveDeliveryAgencyId(override, vendorDefault)` — so the number is verifiable rather than merely
displayed.

⚠ **One deviation:** `status` is validated as a **bounded string, not a pinned enum** — ADR-005
D-17. A vocabulary this service does not own is validated for shape, not membership, or a seventh
`ConnectionStatus` added in jovi-mall becomes silently unfilterable. This matches
`ListRosterQuerySchema` on the very endpoint you told us to mirror, and your own BR says you will
render an unrecognised value rather than reject it. The six values are pinned by a test that
re-reads jovi-mall's model.

## Three errors in our own docs, found while answering this

- `vendors.md` documented `counts.agencyConnections` as a **three-key** object with an invented
  `paused` key. The code returns seven, as your BR correctly quoted.
- `counts.products` was documented as omitting zero statuses. It never does — the reducer starts
  from a fixed empty record, so every key is always present.
- The example omitted `total` and `pendingReview`.

All corrected.
