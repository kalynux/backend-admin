## § 1 — the field is `verification`, top-level, identical to jovi-mall's · **BUILT**

```jsonc
{
  "id": "66a2aabbccddeeff00112233",
  "owner": { "type": "agency", "id": "665c…", "name": "Littoral Express" },
  "status": "pending",
  "origin": "auto_threshold",
  "verification": { "verified": false, "verdict": "pending" },
  "destination": { "...": "unchanged" }
}
```

**Top-level, not nested under `owner`, not flattened.** Of your three candidate shapes it is the
first. The reasoning, since you asked for it to be judged against the use:

- **Same name and shape as jovi-mall's own admin DTO**, field for field. This service already
  passes jovi-mall's vocabularies through unchanged (`status`, `origin`); inventing a second
  name for one fact across two backends is how the pair stops being diffable.
- **Not under `owner`** because `owner` is a *reference* — who is being paid, resolved from a
  directory. This is a fact about the state of a review, refreshed per request. Putting it there
  would also imply it comes from the name lookup, which is the wrong mental model for the next
  person to edit that code.
- **Not flattened to `owner.verified`** for the reason your own brief gives: on an agent,
  `unverified` and `pending` are different facts, and the flattening loses the one that tells a
  reviewer whether there is anything to chase.

`verdict` is `unverified` · `pending` · `verified` · `rejected`. Branch on `verified` only.

**Read fresh per request**, as you asked — never snapshotted. Documented at
`admin/api-doc/api/money.md` § `GET /money/payouts`, with the whole list of properties.

### One correction to your premise, and it is good news

⚠ **wi-admin is not a re-projection on this route — it is a direct read.** Your § 1 opens with
"wi-admin re-projects those payloads", and on `/money/payouts` there is no payload to re-project:
`PayoutRequestReadRepository` reads `payout_requests` out of the shared jovi_mall database
directly (ADR-009 D-1's read side). jovi-mall's DTO never crosses this wire, so its new field
arrived on nothing.

Two consequences:

- **You were even more right to wait than you thought.** There was no field to forward and no
  amount of reading jovi-mall's page would have told you the name, because the name did not
  exist on this side at all. It had to be created.
- ✅ **It does not wait on jovi-mall's deploy.** The verdict is computed here against the same
  three collections, and `kyc_details.status` / `kyc.status` have been written by the review
  endpoints since Phase 9 — the activation split changed what `status` *means*, not where the
  verdict lives. **This ships when wi-admin ships.**

The cost of that independence, stated plainly so it is not a surprise later: there is no shared
package between the backends, so "what counts as verified" is now defined twice. The two are held
together only by `test:money` § 11 here and `test:payout-verification` in jovi-mall. Both fail
closed on an unrecognised verdict, which is the direction that matters.

### It is on the account page too

`GET /accounts/:ownerType/:ownerId/payouts` renders the same DTO and now hydrates the same field.
Leaving it out would not have looked like a bug: the mapper defaults to `unverified`, so every row
of a **verified** vendor's history would have read "unverified" beside their name, with nothing on
screen or in a log to say why.

### ⛔ No filter or sort on `verified` — and this one is a refusal, not an omission

You asked "if the list query will take one". It will not, and the reason is worth having rather
than a shrug:

The verdict lives in `vendors` / `delivery_agencies` / `delivery_agents`; the queue pages over
`payout_requests`. A server-side filter means a three-way `$lookup` keyed on `owner_type` — which
takes the sort off its index, and, more seriously, **widens the one repository whose narrow
projection is the queue's security control.** That projection is why the payout number cannot leak
on this path: not masked by a mapper somebody could forget, but never read. Adding a join there to
serve a filter trades a real guarantee for a convenience.

**Filter in the client.** The queue is scoped by `status` first and the pending page is small. If
that ever stops being true, the right fix is a denormalised verdict on the payout row written at
request time — not a join here. Say the word if it becomes a real problem.

## § 2 — confirmed a bug, fixed on both roles · **you read it exactly right**

🔴 **Your diagnosis was correct in every particular**, including that it was an oversight of the
axis move rather than a decision, and including the secondary point about documents with no
`kyc_details`.

**The new rule: each verdict refuses a REPEAT of itself and admits everything else.**

```
markVerifiedIfNotVerified   { _id, 'kyc_details.status': { $ne: 'verified' } } → 'verified'
rejectIfNotRejected         { _id, 'kyc_details.status': { $ne: 'rejected' } } → 'rejected'
```

| Case | Before | Now |
|---|---|---|
| First review of either kind | ✅ | ✅ |
| **Approve a refused agency (re-review)** | 🔴 `409` for ever | ✅ |
| Reject a verified agency | 🔴 `409` for ever | ✅ records the verdict |
| Approve an already-approved one | `409` | `409` — *"already verified"* |
| Reject an already-refused one | `409` | `409` — *"already rejected"* |
| **Document with no `kyc_details` at all** | 🔴 `409` on its FIRST review | ✅ — `$ne` matches a missing field |

Your secondary point is closed by the same operator: `$ne` matches a document where the path is
absent, so the pre-`kyc_details` rows are reviewable without a backfill. (Backfills are refused
here on principle before production — dev data is disposable — so a fix that needed one would not
have been a fix.)

**What it gives up, so you are not surprised by it:** two administrators submitting *opposite*
verdicts in the same instant now both succeed and the later one wins, where the equality form let
one through and refused the other. That was the only thing the equality bought, and it bought it
by making re-review impossible. Both actions still write audit rows on your side, and the losing
stamp is overwritten rather than lost.

**Your reject-dialog copy was right and should stay.** You declined to invert it to match a
suspected bug — *"inverting our copy to match a suspected bug would entrench it"* — and that was
the correct call. The stated intent was the correct one; the predicate was wrong.

### Vendors: brought in line, in the other direction

⚠ **Your note that vendors were unaffected was right, and there is a second half you could not
see from the repository shape.** `VendorRepository.setKycVerdict` is indeed an unpredicated
`findByIdAndUpdate` — but the *rule* was there, in the service above it: a read, a comparison, and
a `409 VENDOR_KYC_STATUS_CONFLICT` on a repeat. So a rejected vendor did re-verify fine, exactly
as you said.

The asymmetry you flagged turned out to be **mechanism, not policy**, and it ran both ways:

| | Rule | Atomic? |
|---|---|---|
| **Agency** (before) | ❌ one verdict ever | ✅ compare-and-set |
| **Vendor** (before) | ✅ refuse a repeat | ❌ read-then-write |
| **Both** (now) | ✅ refuse a repeat | ✅ compare-and-set |

The vendor's missing half mattered: a read-then-write refuses a second administrator only when
the two are far enough apart in time. Two opposite verdicts in the same instant both read the old
value, both passed the check, and both wrote — no `409` anywhere, and an audit row on your side
claiming a transition that was overwritten a millisecond later. Nothing observable distinguished
that from the guarded version until it happened. The predicate now lives in the write.

**No wire change for vendors** — same endpoints, same code, same messages. The `409` is simply
now true.

### Why neither test suite caught it

Worth knowing, because it is the failure mode this repository keeps meeting:

`jovi-mall/scripts/test/test-agency-kyc.ts` had two assertions on this predicate. When the axis
moved, **they were updated to require the new literal** — `'kyc_details.status': 'pending'` —
so the suite went green over the defect, and its own closing section went on asserting that
"there is deliberately no un-reject … the approval CAS still accepts it", which was the very
thing that had stopped working. An assertion rewritten to match the code cannot disagree with it.

Both now pin the **property** instead: the predicate must refuse a repeat of its own verdict and
admit every other state, and an equality on the verdict axis is refused by name. Reinstating the
old predicate turns three assertions red — verified by actually doing it. A vendor-parity group
was added in the same file (it is now a cross-role rule, so it needs one home, not two).
