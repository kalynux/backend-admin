## Ask 1 — a profile id now finds its account · **BUILT**

`GET /users?search=<24-hex>` tries the term as five ids:

| The term is | Finds |
|---|---|
| a user id | that account (unchanged) |
| a **customer** id | the account that owns that customer profile |
| a **vendor** id | the account that owns that vendor |
| an **agency** id | the account that owns that agency |
| an **agent** id | the account that owns that agent |

It is the shape you proposed: four point reads on `_id`, run only when the term is id-shaped,
each reading `user_id` and nothing else, and the result added to the existing `$or`.

Three things to know when you render it:

- **The row is the account, so its `id` is the user id, not the id that was typed.** The typed id
  is on the detail, as `profiles[].id`. No `meta` field says which kind of id matched. If an
  operator being shown a different id from the one they pasted turns out to confuse people, say
  so and a `meta` hint is a small addition.
- **`role` and the other filters still apply.** `?search=<customerId>&role=vendor` finds the
  person only if they are also a vendor. If your Users screen carries a role filter into a
  cross-link, drop it for an id search.
- **A whole id that belongs to nobody still returns an empty page.** Your "whole id that matched
  nothing" sentence is still needed. Its cross-links to Vendors, Agencies and Agents are not, for
  the reason you gave. The link to Orders is: an order id is not a person.

### Your two questions

**1. Is there an objection to the user directory answering for a profile id? No, and the customer
join is not withheld from tier 3.**

The join was already readable in the other direction. `GET /users/:userId` returns
`profiles[].id` for every role the account holds, the customer profile included, to every holder
of `users.read`. So a Support administrator could already learn which customer id belongs to a
user; what they could not do was start from the customer id. Searching by it discloses the same
pair of ids and no new field: the row that comes back is the ordinary directory row they can
already reach with `?role=customer&search=<phone>`.

**2. `customerUserId` on the order projections: not taken.**

The search closes the gap on every screen at once, including the ones neither of us listed. A
`customerUserId` would have to be added to each projection that serves a `customerId`, and the
next projection to serve one would start without it.

What it would buy is one click: a direct link to `/users/:id` where today you can link to
`/users?search=<customerId>` and land on a list of one row. If that click matters on the order
screen, ask for it on the order detail alone. The customer row is already read there for the
name, so it is one more field on a read that already happens.

### What this changes on your side

- **Order → person now has a link:** `/users?search=<customerId>`. The note on your
  `Order.customerId` type still holds for `/users/:id`, which is still a `404` for a customer id.
- **A `CUSTOMER` ticket entity is now reachable the same way.** `support.md` said it was not
  routable, for the right reason: nothing guarantees whether a ticket carries a user id or a
  customer id. The search does not need to know, because it tries both. Link it to
  `/users?search=<entityId>`, never to `/users/<entityId>`. `support.md` is corrected.

## Ask 3 — a part of an id · **DECLINED**

An id matches whole. Three reasons, in order of weight:

1. **A run of digits is a phone number far more often than the start of an id.** Every decimal
   digit is also a hexadecimal one, so `67011234` is a valid id prefix, and it is also the middle
   of a Cameroonian mobile number. The first eight characters of an id are a timestamp, and
   `6701…` to `69ff…` are the seconds between October 2024 and May 2026, a period accounts on
   this platform were created in. Reading the term as both would add, to a phone search, anybody
   who signed up in that exact second. It would be rare, and when it happened the operator would be
   looking at a person whose phone does not contain what they typed.
2. **Only the start could match, and you draw both ends.** A suffix or a middle cannot be served
   from the index, as your request says. Your table cells show an id as its start and its end, so
   "a part matches" would be true of one end and false of the other. "Only whole" is the easier
   rule to explain, and you already explain it.
3. **Nobody holds a prefix any more.** The partial ids operators had came from the clipboard
   taking the eleven drawn characters. You fixed that. Your drawn head is six characters, below
   the eight-character floor in any case.

Your `amina@` point stands: an operator who sees a part of an email match will expect a part of
an id to. The contract now says that it will not, on every page, which is the other half of your
ask.

If operators do turn out to arrive with id prefixes from somewhere else, such as a log line or a
truncated export, say where from. A prefix match limited to terms containing at least one letter
`a`–`f` avoids the phone collision and could be added then.

## Ask 4 — `GET /audit?search=` · **BOTH DONE**

**1. The three fields are stated in `audit.md`**, in a new section, *What `search` matches*:
`actor.email`, `actor.displayName`, `target.label`. It also says what you found out the hard way:
**the action name, the action family and the target type are not searched.** Those have their own
pinned filters.

**2. A pasted id now matches.** A whole 24-hex term is also matched against `target.id`,
`relatedTarget.id` and `actor.id`.

- `relatedTarget.id` is included because a change that went through four-eyes has the approval
  as its target and the real subject as its related target. Without it, a search for a person's
  id would miss the most consequential rows about them.
- `target.id` is matched as a string, as you noted. It is tried as typed and lower-cased.
- **The read scope still applies.** A Support administrator who pastes an administrator's id gets
  only the rows they could already read. This was measured, see below.
- `targetId` and `actorId` remain the precise filters. `search` answers "anything to do with this
  id"; they answer one question each. Your empty-state routing to them is still right for a
  target that is not a 24-hex id (a session UUID, a composite key).

## Ask 5 — the sentence · **DONE**

On `users.md`, `vendors.md`, `agencies.md`, `agents.md`, `orders.md`, `shipments.md`,
`billing.md` and `support.md`, and stated once for the whole service in

**One change to your wording.** You proposed *"it falls through to the text fields and matches
none of them."* The last clause is not always true: a part of an id that is all digits can match
a phone number, and `670112` matched one in your own table. The pages say the term is **treated
as text**.

**Which ids, per page**, as you asked:

| Page | A 24-hex term matches |
|---|---|
| `users.md` | the user id, **or the id of a customer, vendor, agency or agent profile** |
| `vendors.md` | the vendor id or its user id |
| `agencies.md` | the agency id **or its user id** |
| `agents.md` | the agent id **or their user id** |
| `orders.md` | an order, customer, vendor or checkout-group id. **Profile ids, never a user id** |
| `shipments.md` | a shipment, order, agent or agency id. **Profile ids, never a user id** |
| `billing.md` | the plan id |
| `support.md` | **the ticket's own id only**, not the order, shipment or person it is about. Use `entityId` for those |
| `audit.md` | a target, related target or actor id |

Two rows there were not in your request and are worth a look on your side: a **user id** pasted
into Orders or Shipments matches nothing, and an **order id** pasted into Support matches nothing.
Both are the documented behaviour and neither was changed.
