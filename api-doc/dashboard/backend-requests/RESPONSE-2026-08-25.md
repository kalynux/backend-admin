# BR-014 — `/content` wire shapes

## Your diagnosis was right, including the part about why

`content.md` had thirty-six tables about behaviour and zero about shape. That is not an oversight
of a page — it is what happens when a page is written to explain a **port**. Everything in it
answers "what changed when this moved and why", and a reader who already knew the shapes was the
only reader it imagined. The module that was ported rather than designed here is exactly the one
that would have this hole, and you found it the only way it could be found.

**We checked every row of your table against the source. All eleven are correct.**

Two we want to underline because they are worse than they look:

- **`ListAuthorsQuerySchema` is `z.object({}).strict()`** — so `?page=1&limit=20` is a `400` with
  no hint that the exception is deliberate. A client written from `README.md`'s pagination rules
  gets a hard failure on a correct reading of the docs. That is our bug, not yours.
- **The stripped filters are the important one, and it is not a `/content` quirk.**
  `listQuery` in `core/http/list-query.ts` is **not** `.strict()`, so *every* list endpoint on
  this service silently drops an unrecognised query parameter. `categoryKey` instead of
  `category` returns the unfiltered list, `200`, no warning, on any of them. You are right that
  D-17's argument about stale enum values applies to parameter *names* too. It is now written
  down on `content.md`; widening it service-wide is a separate change with its own blast radius
  and we are not making it inside a documentation fix.

## 2 · `key` versus `id` · **decided: `id`, and the params were renamed**

**`id` is canonical, everywhere.** And we went further than you asked, because the rename costs a
client nothing:

```
/api/v1/content/articles/:articleKey   →   /api/v1/content/articles/:articleId
/api/v1/content/authors/:authorKey     →   /api/v1/content/authors/:authorId
```

**Your URLs do not change.** A param name is not observable to a client — you send
`/articles/getting-paid-on-whatsapp` either way. What moved is the route string, the two param
schemas and `req.params.*`. `ArticleKeySchema` deliberately **keeps** its name: it validates the
string's *format* and is also what `authorId` is checked against, so it is not a param name and
renaming it would say something false about its scope.

We took the rename rather than the one-sentence note because the mismatch is what cost you the
module, and a name that is wrong in one place will mislead again. The stored column is still
`key` and always will be — nothing on the wire exposes it.

⚠ **One test of ours had to be rewritten, and it is worth telling you about**, because it shows
how the confusion got locked in. `test:content` carried:

```ts
t.assert('the paths key on the stable string key, never an ObjectId param', () =>
    contentRoutes.every((r) => !r.fullPath.includes(':id') && !r.fullPath.includes(':articleId')));
```

It **banned `:articleId` outright** — encoding "a param called `id` means an ObjectId" as a rule.
That reasoning was never the guarantee: the *schema* is, and a separate assertion already pins
that no content param schema uses the shared `objectId` validator. The ban was replaced with one
that pins the two names the docs now promise. The old assertion is the same mistake as the banner
in § 3, written as code.

# The thing you did not ask about: **`cover.alt` is now per-locale** ⚠ BREAKING

While answering your BR we were asked whether articles are translatable. They are — five locales
(`en · fr · pt · es · ar`), each with its own title, slug, meta title, excerpt and **full body**.
That was already true and is now documented properly, in a new **"What is translated, and what is
shared"** table.

Checking it turned up one field on the wrong side of that line, and we moved it.

### What changed

```diff
  "cover": {
    "url": "/covers/getting-paid.jpg",
-   "alt": "A market stall taking a mobile payment",
    "width": 1600,
    "height": 900
  },
  "translations": [
-   { "locale": "en", "title": "Getting paid on WhatsApp", … },
-   { "locale": "fr", "title": "Se faire payer sur WhatsApp", … }
+   { "locale": "en", "title": "Getting paid on WhatsApp", "coverAlt": "A market stall taking a mobile payment", … },
+   { "locale": "fr", "title": "Se faire payer sur WhatsApp", "coverAlt": "Un étal acceptant un paiement mobile", … }
  ]
```

**Why:** one article publishes in up to five languages off one image, and a single shared `alt`
put English words into a French screen reader and onto the French page's `og:image`. The image
stays shared — `url`, `width` and `height` are properties of the file, and five uploads before an
article could publish would be busywork. The alt string is prose, and every other reader-facing
string on the document was already per-locale. This one was an oversight, not a decision.

### What you must change

1. **`cover` no longer accepts `alt`.** `CoverSchema` is `.strict()`, so your cover form will
   **400 the whole request** until the field moves. This is the one thing here that breaks.
2. **`translations[].coverAlt`** — `string`, optional on write, `string | null` on read. Add it
   to your translation editor beside `title` and `excerpt`.
3. **A new publish blocker.** `BLOG_ARTICLE_NOT_PUBLISHABLE` can now return
   *"The cover image has no alt text in `"fr"` — …"*, **one row per language**, so the editor
   knows which translation to open. Only **published** translations block: a drafted language
   with no alt text does not stop English shipping.
4. **`updatedAt` now moves when `coverAlt` changes.** It is reader-facing prose, so rewriting it
   is a content revision — same class as editing the excerpt.

### What does NOT change

**The public wire shape.** `GET /api/public/articles/{slug}` still returns
`cover: { url, alt, width, height }`, byte-identical — jovi-mall's projection reassembles it from
whichever translation it is serving. The marketing frontend needed no change at all, and the only
note added on that side is that `alt` now varies by locale, so a cover cache should key on
`(id, locale)` rather than `id`.

Two properties worth knowing: `alt` is **never empty** on the public route (an empty `alt` is the
HTML for *this image is decorative, skip it*, which is a lie about a cover), and it is never in
the wrong language. Publish refuses the case that would produce either.

Covered on both sides — `test:content` §5 and §7, `test:blog`'s public-DTO group — with the two
assertion sets deliberately mirroring each other, since the preview and the published page must
project the same input identically.
