## 2 · Why (a), stated properly this time

The reason is in D-7 already, and neither the ADR nor the api-doc had connected it to the summary.

**The tier-3 boundary is not a confidentiality boundary.** D-7's own words: what Support is denied
is machine detail *"which on a support call is not a secret so much as a false lead"*, and
`failure-exposure.ts` says the same — *"a stack trace in a support conversation produces a customer
being told something wrong with great confidence"*.

So the hazard the boundary exists to prevent is **per-incident causal attribution**: an agent reads
one row and tells a customer their message failed because the `sync identity` node timed out. That
sentence is wrong often enough to matter, and the row is what makes it sayable.

**A summary cannot produce that sentence.** No node, no message, no stack, no per-incident row —
only *this workflow, this channel, this many, since then*. What it supports is *"WhatsApp is
degraded right now, we know"*, which is the exact statement D-7 says Support is granted this
surface in order to make. Withholding the workflow name would have cost the rung its most useful
instrument in order to defend a boundary that was never about the name.

Your guess was right, and your reasoning for it was the reasoning we used.

So the module's rule, now written in all three places: **the feed is graded, the summary is whole.**

## 3 · Two things you did not find, and one of them changes what (b) would have cost

Raised because your report is the record this decision gets read from later.

**`workflowId` is also an ungated query *filter*.** `FailureQuerySchema.workflowId` is available to
every caller and the controller never consults `admin.tier` for it. A tier-3 administrator can
already narrow `/failures?workflowId=…` and gets tier-3 rows back. That is consistent with the
decision above and we have left it alone — but it means **(b) was never one change.** Projecting
the summary's response would have removed the convenient source of ids and left the filter open, so
choosing (b) honestly would have meant deciding the filter too. Worth knowing that the option you
offered as the cheap one was the expensive one.

**Nothing asserted any of this.** `test:automation` § 2 pins the feed's projection hard — down to
*"tier 3 sees NO machine detail — no node, no message, no workflow"* — and asserted **nothing**
about the summary's fields. So the only thing describing the module's boundary was a sentence that
was wrong. **A deliberate asymmetry that nothing asserts is indistinguishable from an accident**,
which is precisely how it read to you. That is the part of this we consider the actual defect, and
it is fixed below.
