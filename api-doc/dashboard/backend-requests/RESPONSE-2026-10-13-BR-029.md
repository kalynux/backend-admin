**Built, in the shape you proposed.** `GET /users` now carries `meta.idMatch.kinds` whenever
`search` was read as an id. All four of your requirements hold and all three questions are

## Your four requirements

| | Requirement | Answer |
|---|---|---|
| 1 | Absent when the term was not read as an id | ✅ **No key at all.** Never `null`. No `search`, a name, an email, a phone and a part of an id all send plain pagination `meta` |
| 2 | Present and empty when a whole id resolved as nothing | ✅ `"idMatch": { "kinds": [] }` |
| 3 | A list, not a single value | ✅ In a fixed order: `user`, `customer`, `vendor`, `agency`, `agent` |
| 4 | An open vocabulary | ✅ Stated in `users.md`. Print an unrecognised kind raw, as you planned |

"Read as an id" is one function, used by both the search filter and this field, so the two cannot
disagree about a term. It is the rule already on the page: exactly 24 hexadecimal characters,
either letter case, nothing round it.

## Your three questions

**1. Can it describe the id independently of `role`, `status` and the date range? Yes.**

Neither read behind the field sees a filter. So:

| Request | `total` | `kinds` | Your sentence |
|---|---|---|---|
| `?search=<customerId>&role=vendor` | 0 | `["customer"]` | "that id is a customer's — the role filter is hiding the account" |
| `?search=<userId>&role=vendor` | 0 | `["user"]` | the same, for an account's own id |
| `?search=<an id that is nobody's>&role=vendor` | 0 | `[]` | "that id is no account's or profile's", and no button |

On the disclosure you raised: it does tell the caller that an id is a customer's without returning
the row. That is accepted. Every holder of `users.read` may send the same search without the
filter, the user directory has no per-tier scope, and the field carries a kind and nothing else:
no account id, no name.

**2. Should it say `user` when the term is the account's own id? Yes.** For your reason: without
it `[]` would mean two things. `["user"]` is an account's own id, and `[]` is nobody's.

This costs one extra read, a count on `users._id`, because "is this a user id" could not be taken
from the page: under `role=vendor` a customer's own user id returns no row and is still a user
id. It runs only for a term that is a whole id.

**3. Per row, or once in `meta`? `meta`.**

There is exactly one case where two accounts come back for one id: the id is one person's user id
**and** another person's profile id. The five kinds of id live in five separate collections, so
nothing forbids it, though nothing in ordinary operation produces it. Then `total` is 2 and
`kinds` is `["user", "customer"]`.

You can still tell the rows apart without a per-row field: **the row whose `id` equals the term
is the `user` one**, and the other arrived through the profile. That is your own derivation,
`row.id !== term`, applied per row instead of to the whole page. A per-row field would only be
needed if two *profile* kinds pointed at two different accounts, which needs two collisions at
once.

## One case you did not list

| Request | `total` | `kinds` | What happened |
|---|---|---|---|
| `?search=<customerId>`, **no other filter** | 0 | `["customer"]` | The profile exists and **its account does not** |

This matters for your *Search this id alone* button. `kinds` non-empty means the id is somebody's
profile; it does not strictly mean an account will come back. The platform never deletes a
`users` row, so this needs a hand-edited database to happen, but if it does, the button leads to
a second empty page.

That second page is not a dead end, though. It has no filter left, so the dashboard can say the
true thing: *this is a customer profile with no account behind it.* That is a data fault worth
reporting, and it is the mirror of the `missing: true` profile on the user detail, where the
account exists and the profile does not.
